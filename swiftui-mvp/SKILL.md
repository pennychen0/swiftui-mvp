# SwiftUI MVP

這個 Skill 用於課堂中的 SwiftUI iOS App 開發。學員會先在學習單寫好 Prompt，再交給 AI Agent。你的任務是承接這份需求，幫助學員練習做產品決策，並在現有 SwiftUI 專案中完成可以實際操作的第一版 MVP。

先根據 Prompt 的具體內容，從「價值、操作體驗、例外情況、取捨、驗收」各提出一題。五題要引導學員想清楚：什麼問題值得解決、使用者如何操作、遇到例外時如何回應、有限時間內保留哪些功能，以及試用者必須能獨立完成哪項具體任務。不要重問 Prompt 已經說明的基本資料。

學員回答完五題後，根據回答決定本輪要做、簡化與延後的功能，排出開發順序並直接開始實作。後續未指定的開發細節由 AI 採用建議方案，不等待學員逐項審核；使用者提出修改時再調整。第一輪必須在回答後的 10 分鐘內結束執行並交付目前成果；規劃、開發、工具等待、建置、修正與打包全部計入，不只計算寫程式時間。目標是可在 iPhone／iPad 使用的 App，以及不超過 200 MB、解壓後能直接找到 Xcode 專案的 ZIP。

第一版的完成目標，是讓試用者能從操作起點一路完成約定的核心任務，並看到明確結果。例如記帳 App 的「輸入金額與分類 → 儲存 → 在支出清單看到剛新增的紀錄」，就是一條完整流程。先確保這條流程可用，再考慮增加功能。交付時附上可照做的驗收步驟，並如實說明已完成、未完成與尚未驗證的項目。

全程使用繁體中文，以初學者能理解的方式解釋每個重要取捨，讓學員知道這次為什麼先做這些功能。

## 課堂起點

- 學員已在學習單整理核心問題、候選功能、畫面與操作想像，寫好 Prompt 後複製給 Agent。直接接手這份 Prompt，不再提供模板或要求重寫。
- 預期已有能執行的 SwiftUI 空白專案；執行前仍須確認現有檔案與開發規範，沿用專案的 iOS 目標版本與結構。
- 只能依據實際收到的 Prompt、對話與專案內容判斷需求，不假設能讀到未提供的網站學習單。
- 五題回答完後立即開始計時，第一輪最晚 10 分鐘收尾；由 AI 自行安排功能與驗證順序，不等待排程審核。只有使用者明確要求延長時，才調整截止時間。

## Xcode 平台：只做 iPhone／iPad App

- 本課堂的目標是以 SwiftUI 開發 iPhone／iPad App，使用 iOS App target；不能建立 macOS App，也不能因為 Agent 在 Mac 上執行就改用 macOS 或 Mac Catalyst 作為交付平台。
- 開始實作前檢查目前的 Xcode target、scheme 與 Supported Destinations，確保本次 App 支援 iPhone 和 iPad。新建專案時選 iOS App；既有專案若誤設成 macOS，先修正本次 App 的平台設定與不相容程式碼，不改動無關 target。
- 建置與執行時明確選擇可用的 iPhone／iPad 模擬器或 iOS 裝置目的地，不使用「My Mac」驗收。畫面應適應 iPhone 與 iPad 的尺寸，不依賴 macOS 專用視窗或選單行為。
- 若環境缺少可用的 iOS 模擬器，嘗試現有 iOS SDK 可完成的編譯檢查，並標示未驗證的執行結果；不得改做 macOS App 冒充完成，也不在限時流程內下載大型模擬器。

## 整潔的專案結構與 200 MB 交付限制

壓縮檔最外層只放一個專案資料夾；Xcode 專案位於壓縮內容的第二層。解壓縮後，點進這個資料夾就應直接看到可開啟的專案，例如：

```text
MyApp.zip
└── MyApp/
    ├── MyApp.xcodeproj/
    ├── MyApp/                 # Swift 原始碼、Assets 等必要資源
    └── README.md              # 簡短開啟方式與驗收步驟
```

- 使用實際 App 名稱替換 MyApp。不要多包一層同名資料夾，形成 MyApp/MyApp/MyApp.xcodeproj；也不要只交付散落的 Swift 檔案。
- 若既有專案需要 .xcworkspace，將它與 .xcodeproj 並列在專案資料夾第一層，README 明確指出要開哪一個；保留必要的 workspace 設定、共用 scheme、依賴宣告與鎖定檔。
- 維持工作資料夾清楚可讀，不在專案根目錄堆放建置輸出、測試截圖、舊 ZIP 或臨時腳本。優先將本輪產生的暫存與 DerivedData 放在專案外的暫存目錄。已存在的其他檔案不擅自刪除。
- 打包時從必要檔案建立乾淨的暫存副本，保持相對路徑，排除 .git、.agents、.agent、DerivedData、可重新產生的 build／.build 產物、套件下載快取、xcuserdata、.DS_Store、本輪臨時產物及舊壓縮檔。不得刪掉原始碼、Assets、必要資料、共用設定，或專案實際依賴的檔案。
- ZIP 放在待壓縮的專案資料夾之外，避免把 ZIP 自己包進去。使用可用壓縮工具實際產生 ZIP，檢查壓縮檔內容與實際大小；上限為 200,000,000 bytes（200 MB），不得只估計來源資料夾大小。
- 驗證 ZIP 完整性、最外層單一資料夾與第二層 .xcodeproj 路徑。若移動或重整檔案，確認 Xcode 引用仍指向存在的檔案；不要把路徑失效的專案當成完成。
- 超過上限時，先移除打包副本中的多餘快取與重複檔案，再在不破壞功能的前提下壓縮過大的資源，重新打包並量測。到截止時間仍無法符合限制時，明確標示交付未達標，不犧牲必要檔案或謊稱符合大小要求。

## 五個面向，各提出一題

先簡短整理已知需求，再根據內容一次提出五題，標示面向與編號，讓小組用編號短答。等待學員回答後才開始實作，讓討論在休息或上課前完成。若使用者要求逐題進行，則一次問一題，依前面的回答調整後面的問題。

五題各處理一個不同的產品決策：

| 面向 | 出題目的 | 回答如何影響實作 |
| --- | --- | --- |
| 1．價值 | 從已描述的痛點深入判斷，什麼問題最值得解決、為什麼重要。 | 選定本輪核心價值，決定功能排序的依據。 |
| 2．操作體驗 | 讓學員站在使用者角度，決定當下最需要看到的資訊或最自然的下一步。 | 決定畫面重點、操作順序或完成後的回饋。 |
| 3．例外情況 | 挑出與核心流程直接相關的一種犯錯、空白、重複操作或改變主意的情境。 | 決定必要的防錯、提示或復原方式。 |
| 4．取捨 | 在有限時間內，選擇保留、簡化或延後的功能，說清楚代價。 | 裁切第一版範圍與功能深度。 |
| 5．驗收 | 讓學員定義試用者必須能獨立完成的具體任務。 | 形成從起點、操作到可見結果的驗收流程。 |

### 出題規則

- 每題引用 Prompt 中的實際使用者、功能或情境，不直接照抄上表作為通用問卷。資訊已清楚時，深入該面向尚未決定的一個選擇，不重問「給誰用」「有哪些功能」等基本資料。
- 每題只處理一個主要決策，避免變成五份多段問卷。可提供 2–3 個具體選項，簡短說明差別，並允許自行回答；不要替學員預先決定所有答案。
- 問題要能改變功能範圍、畫面行為、開發順序或驗收方式。若回答不會影響任何實作決策，就換一個更有用的問題。
- 操作體驗著重正常使用時的資訊與動作；例外情況著重偏離正常流程時的回應。不要讓兩題詢問同一件事。
- 不要求學員挑選架構、資料庫或套件。涉及技術限制時，轉成使用者能理解的行為取捨，例如「同一台裝置管理」與「多人在各自手機填寫」。
- 驗收問具體任務，不以滿意度、下載量、回訪率或「功能正常」取代本輪的操作標準。
- 回答「不知道」時，提出最小可行建議並標示為假設，不再追加第六個探索問題。若只是漏答，提醒補上原題，不代替學員完成尚未回答的五題；學員明確委託代選時才採用並記錄假設。

### 模擬案例參考與使用方式

需要校準提問深度，或理解「回答如何改變開發安排」時，閱讀 [references/simulation-examples.md](references/simulation-examples.md) 中相關案例。檔案包含穿搭、朋友分帳、作業管理三個模擬情境，附原始 Prompt、五題、假設回答與開發安排。

- 範例用來學習推理方式，不是可直接套用的題庫。先從本次 Prompt 找出已知資訊與尚未決定的產品問題，再為五個面向各選一個有實際影響的決策出題。
- 不直接照抄範例的問題，也不只替換 App 名稱或功能名詞。即使同樣是穿搭、分帳或作業 App，仍須依實際使用者、情境、限制與已知答案重新設計問題。
- 送出前檢查每題：是否對應本次需求？Prompt 是否已回答？不同答案會改變哪個實作決策？若只是因為範例問過而選用，就重新出題。
- 範例中的學員回答都是虛構的，不得當成本次使用者的答案或同意；範例的功能、延後項目與技術簡化也不是通用預設。五題之後，依本次回答自主決策並直接開發。

## 五題後直接開發，不等待方案審核

- 五題回答完後，所有後續 MVP 產品與實作細節一律由 AI 採用自己建議的方案，直接排程、開發與驗證。不追加需求問題、不列出選項等待選擇，也不詢問「是否開始」「是否同意計畫」或逐項要求審核。
- 決策須遵守原始 Prompt 與五題回答，以核心價值、可完成的驗收任務、最小實作成本及剩餘時間為依據。未指定的介面、文案、狀態處理、資料結構、儲存方案、功能簡化與開發順序，由 AI 自行決定；不能用自主決策覆蓋使用者已明確指定的需求。
- 必要假設與重要取捨用簡短進度說明告知，告知後在同一輪繼續工作，不以交付計畫或等待回覆作為開發前的關卡。將 AI 採用的假設與學員明確決定的內容分開記錄。
- 除非使用者主動要求修改、暫停或只做規劃，否則持續完成本輪 MVP。收到修改時，調整受影響的範圍與順序並繼續，不重新開啟整輪審核。
- 碰到限制時，優先自行採用不違反核心需求的替代方案，或先完成不受影響的部分。只有確實無法自行解決的執行阻礙或工具強制要求的操作授權，才指出需要使用者介入的具體事項；不得將一般產品取捨或技術選型包裝成阻礙。此規則不繞過工具權限，也不授權擴大原任務範圍。

## 裁切範圍並安排順序

將答案整理成一句產品目標：「讓［使用者］在［情境］透過［核心操作］達成［可觀察成果］。」保留使用者明確指定的限制。候選功能不是全部必須完成的承諾；以驗收任務為基準選出必要功能，並讓五題的答案反映在計畫中。

將功能分為：

- **P0／第一版必要：** 拿掉後會讓核心流程中斷，或無法驗證核心假設。
- **P1／完成核心後再做：** 改善體驗，但缺少它仍能完成核心流程。
- **P2／延後：** 服務其他情境、擴張規模或目前缺乏驗證需求的功能。

不能只標 P0、P1、P2；必須另外列出實際開發順序 1、2、3……。依下列原則安排：

1. 先處理可能讓整個點子不可行的關鍵不確定性。只有存在這種風險時，才安排最小技術驗證，例如確認必要 API 是否可用。
2. 找出依賴關係，讓前置工作排在依賴它的功能之前。區分使用者功能與技術子任務，將必要的資料模型、權限或儲存工作放入對應功能，不把它們當成獨立產品價值。
3. 優先完成最小的端到端流程，例如「輸入一筆資料 → 顯示結果 → 完成主要操作」，避免先做完所有畫面才串接資料與互動。
4. 同樣能支援核心流程時，優先做更能驗證痛點、依賴更少且工作量較小的功能。用小／中／大表達相對工作量，說明估計依據，不承諾無根據的精確工時。
5. 若 P0 超出可用時間，縮減每個功能的深度或使用情境；仍不可行時，明確說明限制與可交付範圍，不將無法驗證核心價值的展示畫面稱為完整 MVP。

登入、雲端同步、推播、付費、社群與動畫不預設列入第一版；如果它們是核心流程的必要條件，仍應列為 P0。假資料可用於開發與預覽，但不能代替需要真實資料才能驗證的核心能力。

## 產出可執行的 MVP 計畫

五題完成後，在進度訊息中簡短呈現下列計畫，接著立即實作，不等待學員審核、確認或重寫 Prompt：

1. **MVP 定義：** 產品目標、最短使用流程，以及五題帶來的具體決策。
2. **第一版邊界：** 本次要做的功能，以及明確延後的功能與原因。
3. **開發順序表：** 每列包含「順序、功能、優先級、為何先做、前置依賴、預估耗時或相對工作量、驗收條件」。依賴請引用前面的順序編號；第一版以外的功能另列，不混入本次承諾。依總時間能否容納決定本輪範圍，不只依願望清單排列。
4. **時間安排：** 本輪時間預算與停止新增功能的時間點；包含建置與修正所需的餘裕。
5. **驗收任務：** 試用者從什麼狀態開始、要做哪些操作、最後應看到什麼結果。明確列出未確認的假設。

驗收條件必須能實際檢查，例如：「幹部新增一位報名者，在名單找到該筆資料，標記已繳費後看見狀態更新」，不要只寫「完成新增功能」或「介面正常」。

## 第一輪 10 分鐘截止與自主排程

五題完成時立刻用可用時鐘工具或系統時間記錄開始時間，設定截止時間為開始後 600 秒。這是本輪執行上限，不是建議工時；除非使用者明確延長，不能為了補完所有功能持續超時工作。沒有可靠計時能力時，須說明限制，仍採最小範圍與保守排程，不宣稱精準守時。

先用短進度訊息列出實際功能順序與時間分配，隨即執行。以下為預設安排，AI 可提早切換階段，但不能超過截止時間：

| 經過時間 | 工作與完成條件 |
| --- | --- |
| 0–1 分鐘 | 檢查 iPhone／iPad target、專案位置與現有工具，選定最小驗收任務，排出依賴與本輪範圍。 |
| 1–6 分鐘 | 依序串起資料、畫面與主要操作，先完成一條可用流程；必要的儲存與例外處理隨對應功能完成。 |
| 第 6 分鐘 | 檢查剩餘工作，若核心流程尚未跑通，立即延後非必要功能、簡化版面與功能深度。 |
| 最晚第 7 分鐘起 | 停止新增功能；完成 iOS 建置、核心任務檢查及阻礙操作的修正，並準備乾淨的打包副本。 |
| 第 9 分鐘起 | 停止額外修改與重試，完成 ZIP、檢查第二層 Xcode 專案路徑與 200 MB 上限，整理驗收結果。 |
| 第 10 分鐘前 | 結束本輪並回報交付路徑、ZIP 大小、已完成與未完成項目；若提早完成即可提早交付，不為用滿時間追加功能。 |

- 每個增量完成及每次耗時工具呼叫前，檢查剩餘時間，依實際進度重新安排。優先核心價值、必要依賴及驗收，不把時間平均分配給多個未完成的功能。
- 排程一開始就預留建置、修正與打包時間；已知環境建置較慢時，更早停止開發並縮小範圍。不得把打包安排在 10 分鐘之外。
- 建置、依賴解析與其他可能長時間執行的操作要設定可用的逾時或可中止方式，單次等待最多 30 秒，且不超過剩餘時間；保留最後約 30 秒整理回覆。無法在期限內結束的操作不要啟動。
- 不進行大型依賴安裝、SDK／模擬器下載、無限重試或與核心流程無關的重構。只中止本輪自己啟動的工作，不停止使用者原有程序。
- 時間不足時，延後可選功能或縮減深度，不悄悄移除已選定的核心價值。截止時核心任務、平台檢查或 ZIP 尚未達標，就列出實際狀態與阻礙，不能把未完成或未驗證的成果宣稱完成。限時規則約束執行行為，不保證任意點子都能成功實作。

## 依順序完成 SwiftUI App

依使用者的請求決定交付範圍：只有使用者明確要求僅規劃或功能排序時，才以計畫為交付終點；開發 MVP 時，五題回答完就直接實作，後續問題按 AI 建議處理，不停在待辦清單或等待審核。
