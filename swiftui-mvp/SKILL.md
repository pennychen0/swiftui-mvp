# SwiftUI 分階段介面探索與實作

課堂網站提供各階段的 Prompt 並引導學員填寫。學員將網站產出的文字貼給 AI Agent 後，本 Skill 依照收到的 Prompt 製作專案。學員會比較介面設計、選擇具體元件，最後完成兩個風格一致且可切換的手機畫面。

**最終成果必須是能以 Xcode 開啟、編譯與執行的完整 SwiftUI iOS App 專案。** Go Wide 與 Remix 先做圖。學員確認混搭預覽後，貼上網站的「完成作品」Prompt，才開始在 Xcode 專案實作兩個畫面與頁面切換。

使用繁體中文、白話與具體元件名稱。遵守 Apple Human Interface Guidelines（HIG），減少缺乏主次、無用途裝飾、套版式排版與空泛文案。保留學員明確指定的風格，不把某種顏色、卡片或漸層一律視為「AI 感」。

## 執行邊界

- **依本次貼上的 Prompt 執行，完成一個階段就停下。** 下一個階段由學員在網站操作後貼入新 Prompt 啟動，不自行跳關，不把一次收到的 Go Wide 當成整個 App 的開發授權。
- 學員可以從空資料夾開始。Go Wide 與 Remix 只處理設計圖。收到「完成作品」Prompt 才建立或接手 SwiftUI iOS 專案。有既有專案就沿用相關設定，不覆蓋無關檔案。
- 不要求學員再回答固定五題、不重做產品訪談、不要求重寫網站 Prompt。資訊足夠就直接工作；只針對確實無法執行的歧義，用一個短問題確認必要資訊。
- 學員用畫面位置、按鈕上的字或日常名稱描述修改，即可作為有效輸入。由 Agent 補上元件名稱，不要求學員先懂 API、架構或設計術語；不解釋題型或出題目的。
- **全程禁止 Computer Use。** 不使用 CUA、桌面／瀏覽器的滑鼠鍵盤自動化、AppleScript／System Events 點選、Accessibility UI scripting 或任何代操 Xcode、模擬器、網站的工具。不得為了產圖、編譯、截圖或上傳改用這些方法。
- 可使用檔案與終端機工具、圖片生成 API／工具、非互動式圖片繪製與渲染、`xcodebuild`、`xcrun simctl` 等非 UI 控制方式。圖片檢視與讀取學員提供的截圖不屬於代操。沒有相應能力時如實說明，提供學員手動操作的短步驟，不假裝已執行。
- 課堂網站負責提供 Prompt 與各階段的填寫引導。Agent 依學員貼入的指令實作，不代擬下一步的網站 Prompt、不填網站欄位，也不代為點下一步或上傳作品。

## 對學員的回覆方式

階段邊界、工具選擇、大小檢查與驗證流程，由 Agent 在內部執行。對學員只提供當下有用的成果、具體改動與下一步，不主動介紹背後的 Skill、限制來源、內部檢查清單或工具禁用規則。

- 開始工作時簡短說正在做什麼；完成後先呈現實際圖片、專案或改動，再給下一步，不複述本文件的規則。
- 停在階段邊界時，自然銜接網站操作，例如「先記下喜歡的地方，再把網站的 Remix 文字貼過來」，不要說「Skill 限制我只能做五張圖」或「規則禁止我做第二頁」。
- 描述元件與使用上的效果，不主動展示架構、API、HIG 條文、建置命令、位元組計算或三次檢查紀錄。詳細技術資訊與檢查結果放交付文件或內部紀錄，學員明確詢問時再說明。
- 交付時保留實用資訊：應開啟的專案、檔案位置、需要時的簡明大小、已完成與尚待手動確認的事情。讓學員知道打開哪個檔案、接著按什麼或看什麼，不傾倒內部檢查輸出。
- 需要學員操作時直接給短步驟，例如「請在 Xcode 執行，點一筆資料進入第二頁，再按返回」，不主動解釋 Computer Use 或工具政策。
- 遇到真實阻礙仍須如實說明缺少什麼、已完成什麼與下一步。不把禁止的操作說成已做、不虛構工具故障，也不謊稱圖片已產出、編譯成功或操作通過。若學員直接詢問限制原因，誠實回答，不編造其他理由。
- 只有確實執行並通過的檢查才可說「已確認／已通過」。情境範例只示範語氣，不能複製其中的完成宣告冒充本輪結果。

## 階段辨識與停止位置

依 Prompt 的實際要求、目前產物與對話辨識，不只比對標題或關鍵字。收到畫面修改要求時留在目前階段。Remix 可以往返多輪，每次回交更新圖讓學員檢查。已確認的選擇可沿用，不重建、不重問。

| 收到的內容 | 本次要產出 | 必須停在哪裡 |
| --- | --- | --- |
| Go Wide：要求五個不同方向、五張手機設計圖 | 五張分開、編號 1–5 的預覽圖 | 不建立 Xcode 專案、不寫 SwiftUI、不做第二頁 |
| Remix：混搭選定元素或修改混搭圖 | 每輪交付一張更新的手機設計預覽圖 | 在圖片上反覆修訂，等學員確認並貼上「完成作品」Prompt |
| 第三階段「完成作品」：描述畫面一、畫面二及切換方式 | 以學員確認的混搭圖實作第一頁與同風格第二頁，接上 Navigation 與返回 | 完成明確要求的兩頁流程，不擴充額外頁面 |
| 加入範例資料／邊緣測試 | 為已實作的畫面補對應資料與 Preview | 只有設計圖時，先等待「完成作品」Prompt 啟動實作 |
| 試用、截圖、打包或上傳準備 | 可用的命令列檢查、交付檔案與手動檢查步驟 | 不代操電腦或網站、不將設計圖當執行截圖 |

## 階段一：Go Wide，只做五張預覽圖

1. 讀取學員貼上的 App 用途、使用者、情境、要幫助完成的事、需要／不需要的功能與風格。保留已知限制，不新增登入、廣告等未要求內容。
2. 針對**同一個手機畫面與主要任務**設計五種有明顯差異的方案。保持用途與核心內容可比較，在資訊主次、分組、布局、文字呈現、元件與操作入口上探索不同做法，不只換色，也不把五張變成五個不同功能頁。
3. 使用現有圖片生成能力或非互動式繪圖／渲染工具，交付 **五張獨立、可直接觀看的圖片檔案**，優先 PNG／JPEG。一張圖只包含一個手機介面，不只給文字描述、程式碼、HTML 原始碼、五張連結占位或一張未拆分的五合一拼圖。
4. 各張標示第 1–5 版，提供圖片本身與可存取路徑。檢視實際圖片，確認共五張、內容未裁切、文字可辨識，並記錄每版主要的元件與設計特徵，供後續引用「第幾版」時使用。
5. 不進入 Xcode、不產生 Swift／專案設定，不先做可執行 MVP。短句告知學員可以在網站記下喜歡的部分，**停下等待 Remix Prompt**，不自行問一整輪問題或代選版本。

若現有工具無法生成或顯示圖片，明確說明「目前未完成五張預覽圖」及缺少的能力，請學員依課堂安排找助教處理；不得偷偷改用 Computer Use、Xcode 或僅用文字宣稱已交付圖片。

## 階段二：Remix，混搭預覽並反覆改圖

1. 對照網站 Remix Prompt 指定的版本與元件，使用 Go Wide 的圖片及設計紀錄混搭。找不到必要參考時，請學員提供相關圖或紀錄。
2. 交付一張能直接看的手機設計預覽圖，顯示選定的混搭風格。以現有圖片生成能力或非互動式渲染產圖，這個階段不建立或修改 Xcode 專案、不寫 SwiftUI，也不編譯 App。
3. 學員可以用位置、文字或元件名稱指出想改的地方。每次根據回饋修改上一張預覽，保留未被要求改動的設計，呈現一張更新後的圖。按需重複，直到學員滿意。不設定固定輪數，也不替學員判定設計已獲確認。
4. 為每次修訂保留可辨識的版本與圖片路徑。學員確認某一版後將它作為實作參考。學員說滿意時，可提醒他到網站取得「完成作品」Prompt，仍停在設計階段。若學員直接貼上「完成作品」Prompt 且未指定其他版本，採用目前最新的混搭圖，無須再問一次。

## 階段三：依確認的設計實作兩頁與 Navigation

- 收到網站「完成作品」的實作 Prompt 才開始寫程式。依 Prompt 製作兩頁與切換方式，以學員確認的 Remix 預覽圖為主要風格參考。若找不到該圖且現有設計紀錄不足以實作，請學員補上圖或指定版本。
- 建立或接手同一個 Xcode SwiftUI iOS 專案。先確定最後交給學員的專案資料夾，直接在該資料夾最外層放可開啟的 `.xcodeproj`。若學員指定目前資料夾作為專案資料夾，就以該資料夾為根目錄。依照混搭圖實作第一頁，再依 Prompt 完成同風格的第二頁並接上導航。沿用已有的適用畫面與設定。
- 第二頁沿用第一頁的共用色彩、字級、間距、元件外觀、圖示與用字方式；依內容需要調整布局，不逐像素複製第一頁，也不重新探索一輪新風格。
- 第二頁完成後，在同一個 App／target 中整合頁間導航。依 Prompt 使用 `NavigationStack`、適當的 `NavigationLink`／路由與系統返回；核對 iOS 目標版本相容性，不以多個獨立 App 或兩張靜態圖代替。
- 從第一頁點指定的元件進入第二頁，傳遞實際選取項目的資料；返回後保留合理的第一頁狀態。不要讓每個項目都開出無關的固定內容。
- 範例資料是課堂展示資料，明確標示，不宣稱已連接真實服務。只做本次兩頁任務必要的互動，不擅自加入後端、登入、同步、推播等功能。

### 範例資料與「邊緣測試」Preview

若同時收到完成作品及加入範例資料兩段 Prompt，在同一輪依序完成。若只收到其中一段，只執行該段，不替學員送出另一段。

以下資料與 Preview 工作以實際收到的要求為準。若目前只有設計圖，單獨收到資料、試用、截圖或打包要求時，說明要先貼上「完成作品」Prompt 才能實作 App。已有可用程式時，依請求處理既有畫面與資料。

將便於修改的範例資料集中放在適合的獨立 Swift 檔或同等簡單位置。依元件需求提供正常資料、沒有資料、資料很多、文字特別長等狀態，並建立命名為「邊緣測試」的 Preview 組。讓各狀態可個別查看，避免把空、長、多筆狀態混成無法辨識的一個畫面；使用目標版本相容的 Preview 語法。

檢查文字換行、截斷、捲動、空白提示與內容遮擋。不能因 Preview 已寫好就宣稱已在 Xcode 看過結果；提供學員手動查看「邊緣測試」的短步驟。

## HIG 與介面品質：三個設計／實作階段都適用

以 [Apple HIG](https://developer.apple.com/design/human-interface-guidelines) 為依據，必要時查閱對應元件官方指引。學員不需閱讀規範或指定 API，由 Agent 將要求落實在圖片與程式。

- **主次清楚：** 任務相關內容先被看見。字級、留白、分組與對比有一致依據，不用無用途統計、重複卡片或大標語擠走主要內容。
- **元件與行為相符：** 選用合適的原生按鈕、清單、表單、輸入與導航。按鈕文字說明實際動作，重要操作不只靠難猜的圖示。參考 [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)。
- **可讀、可點、可適應：** 支援系統文字樣式與 Dynamic Type、足夠對比及點按間距；一般點按區域以 44 × 44 pt 為設計基準。狀態不只靠顏色，圖示按鈕有適當的 VoiceOver 標籤。尊重安全區域、鍵盤與不同手機尺寸。參考 [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)。
- **兩頁一致、可返回：** 第三階段沿用同一套樣式，導航入口能辨識，返回行為符合系統慣例。頁間導航在「完成作品」階段才加入。
- **不假報驗證：** 設計預覽圖是設計草稿，不是 App 執行截圖；編譯成功不是已試過切換；讀到程式碼不是已看過畫面。分清楚程式碼檢查、編譯、命令列取得的畫面與學員手動操作結果。

## 平台、非 UI 驗證與手動試用

- 交付 SwiftUI iPhone／iPad iOS App，檢查 target、scheme、Supported Destinations 與相容版本，不改做 macOS 或 Mac Catalyst；建置目的地不能用「My Mac」。
- 透過 `xcodebuild -list`、明確 iOS 目的地的建置，以及現有 `xcrun simctl` 能力完成可用檢查。DerivedData 放專案之外。沒有模擬器時做可完成的 iOS SDK 編譯檢查並標示限制，不改做其他平台。
- 取得執行截圖時，只可用現有非 UI 命令列／API 能力，且只呈現實際捕捉到的狀態。不能靠 UI 自動化點進第二頁，也不能將 Go Wide 圖片當成第二頁截圖。
- 請學員在 Xcode 手動執行，從第一頁進第二頁再返回、查看邊緣測試，並各截一張手機內容畫面。若不能自動驗證這些動作，提供短步驟並標為待學員確認；不把整個開發工作交還學員。
- 上傳網站由學員操作。協助準備作品說明（App 主題、兩頁用途、如何切換）、截圖與專案資料夾。網站另要求真實文字／照片版本時，只使用學員已提供的內容；缺少素材就指出缺口，不捏造已替換或已上傳。

## 整份交付上限 120 MB，入口在第一層

**學員打開交付的專案資料夾，就要直接看到可雙擊的 `.xcodeproj`。** 入口路徑必須是 `<交付資料夾>/<App 名稱>.xcodeproj`。原始碼與素材可以放在旁邊的子資料夾。ZIP 解壓後，打開裡面唯一的專案資料夾也必須符合這個結構。

**每份完整交付專案資料夾的檔案內容總量，以及對應 ZIP 本身，各不得超過 120,000,000 bytes（120 MB，十進位）。** ZIP 內所有檔案的未壓縮總量也受同一上限約束，不能只靠壓縮把超大的專案藏進小 ZIP。原始碼、必要設定、Assets、範例資料、文件及隨交付附上的設計圖／截圖全部計入；不得拆成多包繞過上限。

```text
MyApp.zip
└── MyApp/                     # 解壓後只需打開這個資料夾
    ├── MyApp.xcodeproj/       # 第一層就看得到，內含 project.pbxproj
    ├── MyApp.xcworkspace/     # 僅在實際需要時並列保留
    ├── MyApp/                 # Swift 原始碼、Assets 與必要資料
    └── README.md              # 開啟方式、兩頁用途與手動檢查步驟
```

- 「Xcode 入口」指真正能開啟的 `.xcodeproj`／必要的 `.xcworkspace`，不是 `.app`、別名、捷徑或單獨 Swift 檔。若產生器多包了一層，交付前整理專案內容並驗證引用，或直接將內層真正的專案根目錄交給學員。不得把仍須再進入 `ios/`、`App/` 或同名子資料夾的外層目錄當成交付根目錄。
- 在乾淨副本中維持可用的相對引用；重整路徑後檢查 source、Assets、workspace 與依賴引用，不只搬專案入口。交付不依賴副本外的檔案或符號連結。
- 從必要檔案打包，排除 `.git`、`.agents`、`.agent`、DerivedData、可再生 build／.build 產物、套件快取、xcuserdata、.DS_Store、舊 ZIP 與暫存。保留必要資源、共用 scheme、依賴宣告與鎖定檔，不擅自刪除原工作區檔案。
- 未被 App 引用的探索過程原圖可留在交付副本之外；保留版號與選擇紀錄，需要附圖時用合適解析度與壓縮，所有附圖仍計入總量。不能移除 App 必需資源來湊大小。
- ZIP 放在專案資料夾之外。超標先清理副本中的快取與重複檔、壓縮過大圖片，重做檢查；仍超標就如實回報不符合，不能只量某個子資料夾或估計大小。
- 專案內容與交付說明整理完成後再打包；打包後若又修改副本中的程式、資源或說明，必須重新打包並檢查，不能交付內容與 ZIP 不一致的兩份成果。檢查過程紀錄可留在交付副本之外。

### 三次實際入口檢查

使用附帶唯讀工具 [scripts/check_delivery.py](scripts/check_delivery.py)，把下列路徑換成實際絕對路徑。工具只證明入口結構與大小，不證明專案引用、編譯與畫面互動。

1. **「完成作品」建立／接手專案後：** `python3 "<skill路徑>/scripts/check_delivery.py" "<專案資料夾>"`。第一次檢查從開始實作時進行。檢查參數要用最後要交給學員打開的資料夾，不能改用其子資料夾取得通過結果。
2. **交付前：** 對乾淨交付副本再次執行工具，確認第一層入口、所有檔案總量與必要設定。可用 Xcode CLI 時對副本執行 `xcodebuild -list -project "<副本>/MyApp.xcodeproj"`（需要 workspace 則用 `-workspace`），並做相容的 iOS 建置。
3. **打包後：** 將最終 ZIP 實際解壓到新的暫存目錄，再執行 `python3 "<skill路徑>/scripts/check_delivery.py" "<解壓位置>/MyApp" --zip "<ZIP路徑>"`。檢查一個外層資料夾、第一層實體入口、ZIP 完整性、資料夾／ZIP／ZIP 內容總量；可用時再對解壓後入口執行 `xcodebuild -list`。

若只交資料夾，仍完成前兩次與大小檢查，第三次標示「未提供 ZIP，不適用」，不能假報解壓通過；需要 ZIP 時必須實際打包並做第三次檢查。工具不可用時做等效命令列檢查。失敗要修正副本並重做受影響檢查。第一層實際清單與詳細檢查結果放交付文件；對學員簡短指出應開啟的專案路徑與尚未通過的項目。

## 課堂時間與每階段回報

- 課堂整體以 30 分鐘為目標，由網站與當次使用者訊息控制階段與截止。順序為 Go Wide 五張圖、Remix 一張混搭圖與按需修訂、收到網站「完成作品」Prompt 後實作兩頁與 Navigation，再檢查並交付。
- 若收到整體截止時間，依實際剩餘時間完成當前階段，預留建置與交付檢查，減少非必要工作；到截止如實回報，不能跨階段替學員作決定。沒有跨回合可靠計時資料時，不宣稱已精準計算學員在網站上的等待時間。
- 每階段完成就交付並停下等下一份 Prompt，不為用滿時間加功能。不大型安裝、不無限重試；長工具操作使用可用的逾時與中止方式。
- Go Wide 呈現五張編號圖片。Remix 呈現最新的混搭圖與本輪具體改動。第三階段提供 Xcode 專案入口、驗證狀態，並說明兩頁如何切換，另有完成範例資料或邊緣測試時也說明如何查看。交付時指出檔案、應開啟入口與待學員確認事項。詳細大小與檢查結果記錄在交付文件，對話按需要提供簡明大小。沒有做的工作不宣稱完成。

需要辨識混合 Prompt 或階段邊界時，閱讀 [references/simulation-examples.md](references/simulation-examples.md) 的情境。案例只是行為參考，不能把案例中的版本、選擇、資料或權限當成本次學員的決定。
