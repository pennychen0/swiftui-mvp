# 五題到 MVP 開發安排：模擬案例

本檔示範提問深度，以及學員回答如何影響功能取捨與順序。所有學員回答均為假設；開發安排是模擬計畫，並非已完成或經實測能在 10 分鐘內交付的成果。

依需要閱讀相關案例：

- 穿搭 App：區分看似相同的痛點，將推薦範圍縮小。
- 朋友分帳 App：由使用者價值決定資訊呈現，將具體任務轉為驗收案例。
- 作業管理 App：讓正常流程與例外處理共同支援核心任務。

## 如何參考

只借用「找出未決問題 → 提出選擇與代價 → 根據回答改變實作」的思考方式，不照抄問句、不套用假設答案。實際出題仍須依本次 Prompt 與對話，每個面向各問一題，等待使用者回答後才實作。

同一主題也可能有完全不同的需求。例如穿搭 App 若已指定「依正式場合搭配」，就不應再照問「懶得挑，還是不知道怎麼搭」；應深入本次尚未決定、會影響核心價值的問題。不要為了符合案例而新增使用者未提出的產品方向。

以下五題後的回應是自主執行的示範：說明方案後立即工作，不再詢問是否同意。實際執行仍須依專案狀態評估範圍，保留建置與修正時間。

## 案例一：穿搭 App

### 學員提供的 Prompt

> 我想做一個穿搭 App，幫助大學生解決每天出門不知道穿什麼的問題。可以加入自己的衣服、依照天氣推薦穿搭、記錄穿過的搭配。首頁希望看到今天推薦穿什麼。

### 五個問題與假設回答

| 面向 | 根據此 Prompt 產生的問題 | 假設學員回答 |
| --- | --- | --- |
| 價值 | 「不知道穿什麼」可能是懶得挑，也可能是不知道怎麼搭。你們最想先解決哪一種？ | 懶得挑。上課前很趕，希望有人直接給一套。 |
| 操作體驗 | 首頁直接給一套搭配，或先讓使用者挑今天的場合，你們覺得哪個比較符合趕著上課的情境？ | 直接給一套，不喜歡再換。 |
| 例外情況 | 推薦的衣服如果正在洗，使用者應該暫時排除那件衣服，還是只能一直換下一套？ | 可以把衣服標成暫時不能穿。 |
| 取捨 | 天氣串接會占用開發時間。第一版先讓使用者選「熱／涼／冷」，再從自己的衣服搭配，能接受嗎？ | 可以，先把推薦和換一套做好，穿搭紀錄延後。 |
| 驗收 | 請描述同學試用時必須完成的一項任務，才能證明這個版本真的能幫他決定穿什麼。 | 加入幾件自己的衣服，選天氣，得到能穿的搭配，不喜歡可以換。 |

### 回答如何改變安排

「減少選擇負擔」成為核心價值；首頁以一套建議搭配為主，不先要求使用者填更多偏好。暫時不可穿的衣物須排除，否則建議無法使用。手動選冷熱與延後紀錄，則是這組學員接受的範圍取捨。

### 五題後，AI 說明並直接開發

> 我會先做「建立衣櫃 → 選擇冷熱 → 取得搭配 → 換一套」的流程。衣服先用名稱、類型和冷熱標籤表示，依標籤組合上衣與下身；這是依目前需求採用的簡化方案。自動天氣與穿搭紀錄延後，接著直接開始開發。

| 順序 | 本輪功能 | 依賴與排序理由 |
| --- | --- | --- |
| 1 | 新增衣物名稱、類型與冷熱標籤 | 推薦必須先有使用者的衣物資料。 |
| 2 | 選擇冷熱並產生一套搭配 | 依賴 1，讓主要任務先能完成。 |
| 3 | 換一套、標記暫時不可穿 | 依賴 1、2，支援學員指定的選擇與例外處理。 |
| 4 | 保存衣櫃，補齊可用衣物不足提示 | 完成可重複使用的流程；必要的排除條件須在推薦時一併處理。 |

本輪核心功能列為 P0；自動天氣與穿搭紀錄延後。預計前 6–7 分鐘開發，剩餘時間建置與檢查；時間不足時先簡化版面，不移除不可穿衣物的排除規則。

驗收任務：新增足以組成兩套搭配的衣物，選擇相符的冷熱條件，取得並更換搭配；將其中一件標成不可穿後，確認不再被推薦。若沒有其他有效搭配，顯示明確提示。

## 案例二：朋友分帳 App

### 學員提供的 Prompt

> 我想做朋友出去玩用的分帳 App。可以建立旅遊群組、記錄誰付了多少錢、自動分帳，還想做花費圖表和提醒朋友還錢。首頁顯示這次旅行的支出。

### 五個問題與假設回答

| 面向 | 根據此 Prompt 產生的問題 | 假設學員回答 |
| --- | --- | --- |
| 價值 | 你們最想改善的是「記不清誰付了什麼」，還是「記完仍不知道最後誰該還誰多少」？ | 後者，每次最後都要另外算。 |
| 操作體驗 | 旅行結束打開 App 時，首頁應先顯示支出明細，還是每個人的結清結果？ | 結清結果，明細需要時再看。 |
| 例外情況 | 有人沒參加某次聚餐時，這筆錢應如何分配：仍由全員平均，還是每筆可以選參與的人？ | 每筆可以選參與者，不然算出來不公平。 |
| 取捨 | 第一版改由一個人在同一台手機管理，先完成分帳計算，群組同步、圖表和還款通知延後，可以接受嗎？ | 可以，先算對，結果給大家看就好。 |
| 驗收 | 請用一個有具體金額的情境，描述你們要怎麼確認分帳結果算對。 | 三人吃飯 600 元由 A 付；B、C 喝飲料共 100 元由 B 付。最後 B 還 A 150 元，C 還 A 250 元。 |

### 回答如何改變安排

核心成果是可信任的結清結果，因此首頁重點由原先支出明細改為結清方式。每筆參與者不能省略，否則無法支援提出的實際情境。單機管理是學員接受的簡化，不是所有分帳 App 都必須採用的方式。

### 五題後，AI 說明並直接開發

> 我會優先完成分帳結果，首頁顯示誰應付給誰多少。採單機管理，每筆支出可以選付款人與參與者；金額輸入、計算精度和刪除錯誤支出由我處理，直接開始實作。

| 順序 | 本輪功能 | 依賴與排序理由 |
| --- | --- | --- |
| 1 | 建立成員與支出資料 | 讓付款人與分攤對象有明確依據。 |
| 2 | 輸入金額、付款人與參與者 | 依賴 1，產生可計算的真實輸入。 |
| 3 | 計算應付與已付差額，顯示結清方式 | 依賴 2，直接交付這組最重視的價值。 |
| 4 | 查看明細、刪除錯誤支出並重新計算、保存資料 | 依賴 2、3，使輸入可修正且下次開啟仍可用。 |

上述核心流程列為 P0，群組同步、圖表與還款通知延後。前 6–7 分鐘完成核心實作，預留最後 3–4 分鐘檢查計算、資料修改與建置。不得用靜態結清數字替代實際計算。

驗收任務：建立 A、B、C 三位成員，輸入學員提供的兩筆支出，確認 B 支付 A 150 元、C 支付 A 250 元。刪除飲料支出後，應重新顯示 B、C 各支付 A 200 元。

## 案例三：作業管理 App

### 學員提供的 Prompt

> 我想做幫大學生管理作業的 App，可以新增課程、記錄作業期限、收到提醒、查看月曆，完成作業後可以打勾。希望畫面簡單，打開就知道有哪些作業。

### 五個問題與假設回答

| 面向 | 根據此 Prompt 產生的問題 | 假設學員回答 |
| --- | --- | --- |
| 價值 | 忘記交作業，和作業很多卻不知道先做哪個，哪個是你們這次最想解決的問題？ | 不知道先做哪個，常常到最後才發現快到期。 |
| 操作體驗 | 打開首頁時，你們希望依課程分組，還是把所有未完成作業依期限排在一起？ | 依期限排，最近要交的放最上面。 |
| 例外情況 | 作業超過期限還沒完成時，應該繼續留在清單醒目提示，還是自動收進歷史紀錄？ | 繼續放在最上面，標示逾期，因為可能還能補交。 |
| 取捨 | 如果本輪只能先完成清單排序或月曆呈現，你們會保留哪個？ | 清單。月曆和通知先延後。 |
| 驗收 | 同學要能完成哪個具體任務，才代表這個版本能幫他安排作業順序？ | 新增不同期限的作業，看出最急的一份，完成後打勾，接著看到下一份。 |

### 回答如何改變安排

學員在乎的是決定先做什麼，因此以跨課程的期限排序支援價值，而不是先建完整課程管理。逾期作業仍需顯示，不能自動消失；完成後的清單變化則屬於驗收任務的一部分。

### 五題後，AI 說明並直接開發

> 我會以「知道現在先做哪份作業」為核心，首頁先列出逾期作業，再依截止時間排列未完成項目。課程先作為作業的文字欄位，不另做課程管理頁；完成項目可以查看與取消完成。接著直接實作。

| 順序 | 本輪功能 | 依賴與排序理由 |
| --- | --- | --- |
| 1 | 新增作業名稱、課程與截止時間 | 建立核心任務所需的資料。 |
| 2 | 依期限顯示待辦，清楚標示逾期項目 | 依賴 1，幫使用者決定現在先做什麼。 |
| 3 | 標記完成、查看已完成項目與取消完成 | 依賴 2，完成後可接續下一份作業，也能修正誤操作。 |
| 4 | 保存資料，補上沒有待辦時的畫面 | 讓流程能持續使用，並清楚表達全部完成的狀態。 |

核心流程列為 P0，月曆與通知延後；不另外展開完整課程管理。前 6–7 分鐘實作，剩餘時間檢查排序、狀態更新、資料保存與建置。

驗收任務：新增逾期、今天到期、未來到期的三份作業，確認清單順序與逾期提示；將第一份標成完成後看到下一份，取消完成後確認它回到適當位置。
